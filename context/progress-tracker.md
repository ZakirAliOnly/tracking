## Decisions Made During Build

_Add decisions here as they are made during implementation._

- Renewal cycle defaults to **yearly** (install_date + 1 year). Revisit if cycles vary.
- `customers.password` stores the client's tracking-app/portal login (as kept in the Excel).
- `customers.phone` added (primary contact number directly on customer, per user request).
- `contacts` table kept but optional — only populated when a customer has named secondary contacts.
- `registration_no` is the natural key used to match Renwal rows to installations on import.
- `total_amount` is a GENERATED ALWAYS AS column — never written from the app. Managed via raw SQL, not Prisma migration.
- **`prisma migrate dev` cannot be used on this database.** The migration history has drifted from the live schema (`sale_price`, `discount`, `amount_paid` and the generated `total_amount` were all applied by hand), so Prisma offers only a destructive reset. Schema changes are applied with direct SQL and mirrored into `schema.prisma`, then `prisma generate`. Applied this way so far: `installations.device_id` made nullable, `installations.received` (boolean, default false) and `installations.sim_no` (text) added.
- **Installation entry was deliberately cut back to seven fields** (per the team, superseding the earlier 30-column `Data entry` mirror): `Client Name`, `Registration No`, `Installetion Date`, `received`, `Amount`, `Sim` (charge) and `Sim Number`. The form and the CSV template carry exactly these. Everything else the workbook holds — contacts, address, remarks, vehicle make/model/engine/chassis/colour, IMEI, FM module, cut-off, the other payment columns and `Accunt` — is **no longer captured on entry**.
- `Amount` → `installation_pay`, `Sim` → `sim_payment`. The generated `total_amount` is the sum of the two, since `device_payment` and `net_payment` stay 0.
- `next_renewal_date` is still derived as installation date + `RENEWAL_MONTHS` and is not asked for; it advances through the Record renewal modal.
- `installations.discount` and `installations.amount_paid` are no longer written — they are not columns in the sheet. The columns remain in the DB. **`actions/reports.ts` reads `amountPaid` for the Sales report's "collected" / "remaining" figures, so those now show 0** until that report is reworked.
- Import idempotency key is now **`(orgId, vehicleId)`** — one vehicle carries one installation, so re-entering a registration updates it in place. The old IMEI-based key and its two conflict types are gone with the IMEI field.
- **Import runs a read-only preflight first** (`lib/import-plan.ts` → `checkInstallationImport`). Every row is classified `create` / `update` / `conflict` / `duplicate` / `invalid` and nothing is written until the user has seen it. The import action **rebuilds the plan server-side** rather than trusting the browser's classification.
- **The CSV template states each column's format in its own heading** (`Installetion Date (YYYY-MM-DD)`), because the team fills the file in Excel where nothing else is on screen. `normalizeHeader` strips a trailing bracket group, so bracketed and plain headings match the same column and older files keep importing. Dates are read **day-first** — `2026-01-15` and `15/01/2026` both work, `01/15/2026` is rejected rather than guessed at, and Excel's locale reformatting is the thing to watch when a row fails.
- Rows duplicated **within one file** (the same Registration No on two lines) are all held back — there is no safe way to guess which line was meant.
- `registration_no` is matched **case-insensitively** everywhere so `bhn-058` cannot become a second vehicle beside `BHN-058`. Existing plates keep their stored spelling; only new ones are written normalised (trimmed + upper-cased).
- Unknown `Accunt` values are auto-created as payment methods during import and listed back in the result summary, rather than failing the row.
- **`Client Name` is the sole identity of a customer** (case-insensitive), in both the CSV import and the New installation form. No match creates a new customer; the Mobile Number is never used for matching, only stored. Consequence to watch: two real customers sharing a name are treated as one.
- The form's Client Name is a search box with live suggestions, not a dropdown — the old `customerId` field is gone, so the server resolves the customer by name exactly as the import does. Renaming a customer is no longer possible from this modal (it belongs on the Customers page).
- A new customer with a blank `Mobile Number` is allowed and is created with an empty phone — the row is no longer rejected. A blank cell never overwrites a phone number already stored.
- **All phone/mobile fields are fixed at exactly 11 digits.** `components/ui/PhoneInput.tsx` enforces it while typing (strips non-digits, caps at 11); the Zod schemas re-check on the server. Optional phone fields still accept blank. Supplier phone was previously unvalidated — it now follows the same rule.
- **Errors surface as toasts, not inline banners.** `components/ui/ToastProvider.tsx` is mounted in the root layout; forms call `useActionToast(state?.error)`. The old red boxes were removed from all 12 forms, so do not reintroduce them.
- **An installation can fit several devices, so there is a new table: `installation_devices`** (installation_id, device_id, quantity, unit_price). Applied by hand with `prisma db execute` from `prisma/manual/20260806_installation_devices.sql` and mirrored into `schema.prisma` — purely additive, nothing existing altered. **ids in this schema are `TEXT`, not `uuid`** (Prisma's default for `String @id`); declaring the FK columns as `uuid` fails with an incompatible-types error. `installations.device_id` is kept and set to the **first** fitted device so every existing row and read path still works.
- **The devices price the job, but the Amount stays editable** — it is pre-filled with the combined sale price and can be typed over, the same freedom the CSV import's Amount column has. The per-device prices are still read from stock server-side for the line records; only the overall Amount comes from the form. Use Discount when the reduction should stay visible.
- **A device is a stock line with a `quantity`, not one row per unit** — so fitting devices decrements `devices.quantity` by the line quantity; it does **not** set `status = "installed"`, which would hide the whole remaining line from the Stock page. `moveStock` in `lib/installation-write.ts` nets the previous lines against the new ones inside the same transaction, so re-saving identical lines moves nothing, reducing a quantity returns the difference, and removing a line returns all of its units. The line rows are then replaced wholesale rather than diffed. Verified against the live DB in a rolled-back transaction.
- Refusals rather than silent bad data: out-of-stock lines are listed but disabled and rejected server-side, over-ordering is refused with how many are actually left, **the same device on two rows is summed before that check**, a device with no sale price is refused, and at least one device is required whenever the org holds any stock line at all.
- **`lib/device-options.ts` vs `lib/devices.ts` is a deliberate split** — the type and the label/price helpers have no imports so the entry forms can use them; the Prisma queries sit in the other file. Importing the query module from a client component would pull Prisma into the browser bundle.
- **The `received` tick is gone from both installation forms.** Staff now enter a **Discount** (Rs or %) and the **Amount Paid**, and `received` is derived as `amountPaid >= payable`. `lib/installation-money.ts` (`resolvePayment`) owns that arithmetic and is imported by both the forms — for the live summary — and both Server Actions, for what is stored; it has no imports of its own so it stays client-safe. A percentage is resolved to rupees before writing: `installations.discount` holds rupees only and the entered mode is not kept. `installations.discount` and `installations.amount_paid` are written again after being dormant, which is what makes the Sales report's collected / remaining figures real.
- The CSV import still has its own explicit `received` column and does not carry discount or amount paid — an imported row therefore shows Received with 0 paid, and the installations table reads `received` first when working out what is still owed.
- `actions/reports.ts` was reading `devicePayment` as an installation's worth, which has been 0 since entry was cut back — it now uses `payableOf()` (generated `total_amount` less `discount`), so revenue no longer reports as zero next to a real collected figure. The needless `as any` casts on installation rows went with it; the two on supplier invoices remain.
- **An installation now records which payment method the money went to.** `installations.account_id` existed and was already displayed, but nothing wrote it. Both entry forms ask for it and it is **required whenever the org has an active account**, not shown when it has none — `resolveInstallationAccount` in `lib/accounts.ts` decides that server-side and re-checks the submitted id against the org, so the Zod schema stays shape-only (it cannot see the DB). `lib/accounts.ts` also owns `listActiveAccounts`, the query previously copied into the renewals and suppliers pages.
- **`InstallationRecord.accountId` is optional on purpose: `undefined` ≠ `null`.** Absent means "caller has no opinion" (the CSV import) and the key never reaches the update payload, so re-importing a plate keeps a hand-picked payment method; `null` means "deliberately none" and clears it. Folding `accountId` into `installationData` would silently wipe accounts on every re-import. Verified against the live DB in a rolled-back transaction.
- **Confirmed: `installations.total_amount` really is `GENERATED ALWAYS AS` (`is_generated = ALWAYS`)**, summing the four payment columns — the migration files do not show it, but the live column does. Installation money therefore reaches the Payment Methods balance as soon as an account is attached. Both installation actions now `revalidatePath("/payment-methods")`.
- Follow-ups left open: `actions/renewals.ts` still writes a client-supplied `accountId` with **no org check** — it should call `resolveInstallationAccount`'s sibling logic; and `AccountOption` is still declared separately in `RecordRenewalModal`, `PaySupplierModal` and `TransferFundsModal` instead of importing from `lib/accounts.ts`.
- **A customer can be created with its first installation in one submit.** The Add customer modal's optional installation block posts alongside the customer fields; `upsertCustomer` validates it with `customerInstallationSchema` (`installationFormSchema` minus `customerName`) and runs `customer.create` + `writeInstallation` in one transaction, so a bad Registration No leaves no orphan customer. The option is **add-only** — editing an existing customer never shows it, since adding a second installation belongs on the Installations page. The Client Name search box stays out of this form: the customer being saved *is* the identity, so `customerId` is passed directly and no name matching runs.
- **Double-submit is blocked in one place: `components/ui/SubmitButton.tsx`.** Every submit button in the app is now that component; it reads the enclosing form's `useFormStatus()`, so it disables itself and spins for as long as the Server Action is in flight. This replaced fourteen hand-written buttons, two of which (delete account, delete supplier) and the sign-out button had no guard at all and could be fired twice. Forms no longer take `isPending` off `useActionState`.
- **Every overlay panel is a centered modal with a blurred backdrop — there are no slide-in drawers left.** All twelve were converted and the seven `*Drawer.tsx` files renamed to `*Modal.tsx`. New panels follow the pattern in `ui-registry.md`; do not reintroduce `translate-x-full` side panels.
- **A purchase invoice can now record which payment method its "amount paid now" came out of.** `purchase_invoices.account_id` was added by hand (`prisma/manual/20260808_purchase_invoice_account.sql`, since `prisma migrate dev` still can't run here) and mirrored into `schema.prisma`, nullable, purely additive. `NewInvoiceModal` only shows the Payment Method select once Amount paid now is greater than 0 — required at that point, hidden again (and the field cleared) when it drops back to 0. `resolvePayingAccount` (`lib/accounts.ts`) is `resolveInstallationAccount`'s sibling for this "only required when actually paying" shape: 0 paid needs nothing, something paid with no accounts set up yet is still allowed, something paid with accounts available is required and re-checked server-side. `payment-methods/page.tsx`'s balance sum now subtracts `purchaseInvoice.amountPaid` the same way it already subtracts `supplierPayment.amount`.
- **Fixed along the way:** `fetchSupplierLedger` (`actions/supplier-ledger.ts`) was debiting an invoice's full `totalAmount` but never crediting its `amountPaid`, so the ledger's running balance overstated what was owed on any invoice that had money paid upfront — the Suppliers page's own "Est. payable" figure already subtracted it, the ledger just didn't. It now adds a `payment` entry ("Paid at purchase via …") alongside the `invoice` entry whenever `amountPaid > 0`.
- **Recording a renewal from the toolbar is now Customer + Vehicle dropdowns at the top of one flat page, replacing the old flat "customer · reg no" combined dropdown.** First pass used a staged 3-step reveal (search box → vehicle appears → rest of form appears); on request this was simplified to two plain `<select>`s (Customer, then Vehicle — its options scoped to the picked customer, disabled until one is picked) with every other field (dates, Payment Method, Amount, SIM & Osting, Net, Other) always visible below on the same page, not conditionally mounted — only the Save button waits for a vehicle to be picked. The row-triggered **Record** button on the Renewals table is untouched — it already knows the vehicle and shows the read-only customer/vehicle card instead of the dropdowns. Payment Method is now **required whenever the org has active accounts** (previously always optional with a "No account" choice), and `actions/renewals.ts` now resolves it through `resolveInstallationAccount` instead of writing a client-supplied id with no org check — this closes a gap this file had flagged as a follow-up.
- **The Add customer modal can now save several installations in one submit, not just one.** The single optional installation block became a repeatable array of `InstallationBlockFields` (`components/customers/InstallationBlockFields.tsx`), each fully controlled as an `InstallationDraft`, with an **Add another installation** button below the stack (same disabled-at-one-left rule as `DeviceLines`). The whole array is serialized to one hidden `installationsJson` field on submit instead of using per-field `name`s, because N blocks each with their own repeatable device lines would otherwise collide on `formData.getAll("deviceId")`. `upsertCustomer` parses and validates every entry with `customerInstallationSchema`, refuses the submit outright if two blocks share a registration number (case-insensitive), and resolves each block's devices **sequentially** through `resolveInstallationDevices`'s new `reserved` parameter so two blocks cannot both fit units that only exist once in stock — then writes every block under the one new customer inside a single transaction. Edit mode and the plain Installations-page form are untouched.
- **Rebranded from blue to a white + red minimal palette.** `app/globals.css`'s `@theme` block was rewritten: `--color-accent` is now `#E11D48` (crimson) instead of `#2D6BFF`, backgrounds/borders/text shifted from blue-tinted grays to warm neutrals, `--color-violet` shifted to wine (`#9D174D`) so the 4th categorical color stays in the red family, and `--color-error` was kept a deliberately different orange-leaning red (`#DC2626`) so danger/overdue states don't read as the same color as brand actions. Success (green) and warning (amber) were left alone — they carry financial meaning (received / due) and removing them would hurt readability, not just aesthetics. Every component that read the token (`bg-accent`, `var(--color-accent)`, etc.) picked the new color up for free; the handful of components with **hardcoded** hex/rgba literals (logo + avatar gradients in `Sidebar.tsx`/`LoginForm.tsx`, the six-tone `AVATAR_GRADIENTS` arrays in `CustomersView.tsx`/`RenewalsView.tsx`/`InstallationsView.tsx`, and every card/button `boxShadow` string) were edited directly — the avatar rainbow (blue/green/violet/amber/pink/sky) was replaced with a six-tone red/wine/charcoal set so avatars stay distinguishable without reintroducing off-brand hues. `context/ui-tokens.md` was rewritten to match exactly — it is the checked-in source of truth for these values, do not let it drift from `globals.css` again.

- **Server-side pagination + URL-driven filters on Installations, Renewals, Expenses, Stock and Suppliers.** Every filter tab used to filter a fully-fetched array in React state; now `page.tsx` reads `searchParams` (Next 16 passes it as a `Promise`), runs a paginated `findMany` + a matching `count`/`aggregate` with the *same* `where`, and the filter tabs are `<Link>`s that write `?status=…&page=1` instead of `useState`. New shared pieces: `lib/pagination.ts` (`PAGE_SIZE = 25`, `parsePage`, `pageWindow`, `buildHref`) and `components/ui/Pagination.tsx` (Prev/Next + "Showing A–B of N", extending the table-footer convention in `ui-registry.md`). Customers and Payment Methods were explicitly left out of this pass.
- **Renewals' `received` status can't be expressed as a plain Prisma `where`.** It depends on the installation's *latest* renewal record matching its current due date — a same-row cross-table comparison. `lib/renewals-query.ts` does the whole listing (filter, count, "due soon" badge count) as raw SQL (`$queryRaw` with a `latest_renewal` CTE) rather than approximating it, verified row-for-row against the old full-scan JS logic in a throwaway script before replacing it. "Today" is passed in from JS rather than using Postgres's `CURRENT_DATE`, so the displayed days-until-due doesn't drift by a day against the DB server's own timezone.
- **Suppliers has two independently paginated tables behind one tab** (`?tab=`, `?spage=`, `?ipage=`) — `components/ui/Pagination.tsx` takes an optional `paramName` prop so two `<Pagination>`s on the same page don't collide on `?page=`.
- Stock's stat tiles (In stock/Faulty/Returned) and Suppliers' (`totalSuppliers`/`itemsSupplied`/`totalPayable`) moved from summing every loaded row in JS to `groupBy`/`aggregate` queries — both a pagination requirement (the stats are org-wide, not page-scoped) and a real perf win on their own.

- **Renewals filters cut from four tabs to three: Pending (default) / Received / All, with a due-date range beneath them.** "Pending" is simply `NOT is_received` — overdue, due-soon *and* far-future alike — so nothing unpaid can hide behind a date threshold the way it could when the default tab was "Due soon". The old `due_soon`/`overdue` tabs are gone as filters, but the four *statuses* (`overdue`/`due_soon`/`upcoming`/`received`) still drive the per-row badges, so the distinction is still visible in the table, just not something to filter down to. The red badge on Pending and the "N renewals need attention" banner both still count overdue + due-soon only, and are deliberately **org-wide — they ignore the date range**, since they are a standing alert rather than a view of whatever window is being browsed.
- The date range is a plain `method="GET"` form posting `from`/`to`, not client state — same mechanism as the `<Link>` filter tabs, no JS needed, and omitting `page` from the form naturally resets to page 1. Both ends are inclusive and independently optional. `page.tsx` rejects anything that isn't `YYYY-MM-DD` rather than trusting the query string, and silently swaps a backwards range (`from` later than `to`) instead of returning a confusing empty table. Verified against the live DB, including a temporary backdating of two installations (restored in a `finally`, restore then re-asserted) to prove Pending really does pick up overdue and due-soon rows and that the badge counts them.

- **New Sales Report module (`/sales-report`, sidebar → Main, directly under Renewals).** A per-installation earnings view: Client / Registration No / Install Date / **Sim** / **Device** / **Other**, over four KPI cards — Others (the headline figure, in success green), SIM total, Device total, and installation count. Dated by `installationDate`, since a sales figure is about when the work was done rather than a snapshot of the book. Reuses the Renewals date-range pattern exactly (plain `method="GET"` form posting `from`/`to`, both ends inclusive and optional, Clear link) and the shared `Pagination`.
- **"Other" here is computed, not the stored `installations.other_amount` column** — it is `total_amount − sim_payment − device_payment`, i.e. what the job earned once the SIM and the device (both pass-through costs) are taken back out. The stored `other_amount` is still what the CSV import writes and is left alone; the two can and do disagree (BHN-058 stores 2000 but computes 8000), so do not treat them as the same number. Because `total_amount` is `GENERATED ALWAYS AS (installation_pay + sim_payment + device_payment + net_payment)`, this arithmetic reduces to `installation_pay + net_payment` — worth knowing if the generated expression is ever changed.
- **The KPIs come from a Prisma `aggregate()` over the whole filtered range, not the 25 rows on screen** — a total that only counted the current page would be silently wrong the moment the list paginated. Verified at several ranges that the aggregate equals the sum of the per-row figures the table renders.
